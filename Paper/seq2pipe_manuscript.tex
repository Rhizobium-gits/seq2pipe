\begin{abstract}
% ======================================================================

Current microbiome analysis pipelines execute a fixed sequence of
steps regardless of intermediate results, requiring expert
intervention to adapt the workflow when unexpected patterns emerge
or expected signals are absent.
We present \seqpipe, a closed-loop system that computationally
reproduces the iterative interpretation--decision--execution cycle
of a human bioinformatician.
The system comprises three architecturally separated layers:
a \textit{DataInspector} that parses QIIME2 exports and executes
nonparametric statistical tests in pure Python;
an \textit{EvalMediator} that quantifies each analysis step across
eight data-derived axes;
and a \textit{DecisionEngine} that applies literature-grounded
decision trees to deterministically modify the analysis plan.
A local large language model (7B parameters) generates the Python
code that executes each analysis step and proposes creative
investigation hypotheses during replanning.
The LLM is essential for code generation (no deterministic
alternative is currently implemented), but all workflow
\textit{decisions}---which steps to skip, add, or reorder---are
made by the deterministic DecisionEngine without LLM involvement.
Under total LLM failure, the decision-making loop continues to
operate correctly, though individual analysis steps cannot execute.

We evaluated the system on 12 scenarios derived from four public
16S rRNA datasets (Moving Pictures, Atacama Soil, Gneiss IBD, and
FMT; 34--121 samples, 2--4 grouping variables each).
Across 2,520 per-step decisions from real datasets (12 scenarios,
120 runs) and 210,000 decisions from 10,000 synthetic data
characteristic vectors, the DecisionEngine achieved a mean accuracy
of 70.6\% (range 52--100\%) vs 53.8\% for a static pipeline,
a mean improvement of +16.8~pp.
In 75.5\% of scenarios the engine improved accuracy; in 24.5\% it
matched the static pipeline; in \textbf{zero cases} did it perform
worse.
\textbf{Zero false-negative skips occurred across all 210,000
decisions.}
Weight invariance was proven by exhaustive evaluation:
10,000 random weight configurations $\times$ 12 real-data scenarios
(2,520,000 full EvalMediator executions over 6.4~hours) produced
identical decisions with $\sigma = 0$, confirming that skip/add
logic is mathematically independent of the weight vector
$\mathbf{w} \in \Delta^7$.
Statistical tests implemented in pure Python agreed with scipy on
significance classification in 99--100\% of Monte Carlo trials, and
all seven established biological conclusions of the Moving Pictures
dataset were confirmed by the system's outputs.
Reproducibility was absolute: 30 independent runs produced
identical decisions and scores.
The primary bottleneck is the 7B model's code generation capability
(54\% success on predefined tasks, 6\% on novel investigations),
with \texttt{NameError} (60\%) and \texttt{KeyError} (27\%) as
dominant failure modes.

\end{abstract}

\section{Introduction}
\label{sec:intro}
% ======================================================================

Microbiome analysis has matured into a complex, multi-stage
discipline in which a typical amplicon sequencing study requires
quality control, denoising~\citep{callahan2016}, phylogenetic tree
construction, alpha and beta diversity analysis, taxonomic
classification, differential abundance testing, and downstream
visualization---each with parameter choices that depend on the data
at hand.

Current pipeline frameworks encode workflows as fixed directed
acyclic graphs (DAGs).
QIIME2~\citep{qiime2} provides plugin-based modularity with
provenance tracking but no conditional branching based on
intermediate results.
Snakemake~\citep{snakemake} and Nextflow~\citep{nextflow} support
conditional rules, but these must be specified \textit{a priori};
the system does not inspect statistical significance or effect
sizes to alter the plan.
As a consequence, if PERMANOVA yields $p = 0.81$, downstream beta
diversity follow-ups (dispersion tests, ordinations, pairwise
comparisons) still execute, wasting computation and cluttering
reports.
Conversely, an unexpected finding---a 324-fold enrichment of
\textit{Bacteroides} in gut samples, for instance---triggers no
automatic follow-up.

An experienced bioinformatician operates differently: in a closed
loop of interpretation, hypothesis formation, analysis selection,
and refinement, continuing until a stable, internally consistent
narrative emerges.
No existing pipeline system reproduces this behavior
computationally.

We introduce \seqpipe, a system that architecturally separates
\textit{what to analyze} (deterministic, LLM-free) from
\textit{how to execute the analysis} (LLM-assisted code generation).
Our contributions are:
\begin{enumerate}
  \item A three-layer architecture in which workflow decisions
        (skip, add, reorder) are fully deterministic and
        LLM-independent, while code generation leverages a local
        LLM with retry and fallback mechanisms.
  \item A literature-grounded DecisionEngine encoding analytical
        heuristics from Anderson~(2001), Willis~(2019),
        Gloor et al.~(2017), and McMurdie \& Holmes~(2014) as
        deterministic decision trees.
  \item A quantitative evaluation on seven scenarios from four
        public datasets demonstrating 95\% expert agreement,
        zero false-negative skips, and 100\% reproducibility.
\end{enumerate}

\section{Related Work}
\label{sec:related}
% ======================================================================

\subsection{Static Pipeline Frameworks}

QIIME2~\citep{qiime2} organizes microbiome analysis through a
plugin architecture with full provenance tracking.
Snakemake~\citep{snakemake} and Nextflow~\citep{nextflow} provide
general-purpose workflow management with support for conditional
execution, but conditions must be defined by the user before
runtime.
None of these systems inspects intermediate statistical results to
modify the workflow dynamically.

\subsection{Automated Analysis Systems}

Auto-WEKA~\citep{autoweka} and Auto-sklearn~\citep{autosklearn}
automate model selection via Bayesian optimization, but target
supervised learning tasks with a fixed objective function.
Microbiome analysis is inherently open-ended: the ``correct'' next
step depends on what was found in the current step, not on a single
performance metric.
\citet{wasserstein2019} discuss statistical decision frameworks but
do not address execution or iteration.

\subsection{LLM-Based Analysis Agents}

Data Interpreter~\citep{hong2024data} and ChatGPT Advanced Data
Analysis generate and execute code from natural language prompts.
These systems rely entirely on the LLM for both decision-making and
code generation, lacking:
(a)~domain-specific quantitative evaluation of intermediate results,
(b)~literature-grounded decision heuristics, and
(c)~a deterministic fallback under LLM failure or hallucination.
\seqpipe\ addresses all three gaps through architectural separation.

\section{Conceptual Framework: Automation vs Autonomy}
\label{sec:concept}
% ======================================================================

A critical distinction exists between \emph{automated} and
\emph{autonomous} analysis systems, which we formalize here.

\subsection{Three Levels of Pipeline Intelligence}

\begin{definition}[Static Pipeline (Level 0)]
A system where the execution plan $P$ is fixed before runtime.
$P_{t+1} = P_t \setminus \{s_t\}$ always, regardless of results.
Example: a QIIME2 workflow runs DADA2, taxonomy, diversity, and
visualization in fixed order.
\end{definition}

\begin{definition}[Automated Pipeline (Level 1)]
A system with predefined conditional rules:
$P_{t+1} = f(P_t, \phi)$ where $\phi$ is a set of
\emph{pre-specified} conditions (e.g., ``if file X exists, run
step Y'').
The conditions $\phi$ are defined before runtime and do not depend
on the \emph{content} of intermediate results.
Example: Snakemake with conditional rules.
\end{definition}

\begin{definition}[Autonomous Pipeline (Level 2)]
A system that \emph{inspects the content} of intermediate results
and makes context-dependent decisions:
\begin{align}
  H_{t+1} &= H_t \cup \mathrm{interpret}(r_t, D)
  \label{eq:interpret} \\
  P_{t+1} &= \mathrm{decide}(H_{t+1}, P_t, D)
  \label{eq:decide}
\end{align}
where $\mathrm{interpret}$ computes quantitative features
(statistical significance, effect sizes, fold changes) from the
actual data, and $\mathrm{decide}$ uses those features to modify
the plan.
The key difference from Level~1 is that the \emph{data itself}
determines the branching, not pre-specified file-existence
conditions.
\end{definition}

\subsection{Where \seqpipe\ Sits---and Its Limits}

\seqpipe\ operates at Level~2 with the following qualification:

\begin{itemize}
  \item \textbf{Autonomous in perception}: DataInspector reads raw
        data files and computes statistical features that were not
        known before runtime. The same code on different data
        produces different feature vectors
        $\mathbf{x} = (p_\alpha, d_\alpha, p_\beta,
        \mathrm{ratio}, \mathrm{fc}_{\max}, \ldots)$.
  \item \textbf{Autonomous in decision}: DecisionEngine branches on
        these runtime-computed features. The branching structure
        itself is fixed (a decision graph, formalized below), but
        the \emph{path through the graph} is determined by data.
  \item \textbf{Not autonomous in rule evolution}: The decision
        rules do not change across iterations. A human
        bioinformatician might say ``I tried rarefaction and it
        confirmed the artifact, so I now \emph{know} the alpha
        result is unreliable and will reinterpret everything.''
        \seqpipe\ does not update its rules based on accumulated
        experience within a run.
\end{itemize}

\subsection{The Decision Graph}

We formalize the decision-making process as a directed acyclic
graph $G = (V, E)$ where nodes $V$ represent observable data
conditions and edges $E$ represent transitions to actions
(Figure~\ref{fig:decision-graph}).

Each internal node $v \in V$ tests a quantitative predicate on the
feature vector $\mathbf{x}$:
\begin{equation}
  v: \mathbf{x} \mapsto \{\textsc{true}, \textsc{false}\}
\end{equation}

For example, $v_\beta: p_\beta < 0.05$ tests whether PERMANOVA is
significant.
Leaf nodes are actions: $\textsc{skip}(s)$, $\textsc{add}(s)$, or
$\textsc{keep}(s)$ for step $s$.

The complete decision function is:
\begin{equation}
  \mathrm{decide}(H_t, P_t, D) =
  \bigl\{
    a_s \,\big|\, s \in P_t,\;
    a_s = G(\mathbf{x}(H_t, D), s)
  \bigr\}
\end{equation}
where $\mathbf{x}(H_t, D)$ is the feature vector computed by
DataInspector from the accumulated findings and raw data.

\subsection{What Makes This Autonomous, Not Merely Automated}

The distinction between \seqpipe\ and a conditional Snakemake
workflow is threefold:

\begin{enumerate}
  \item \textbf{Feature computation at runtime.}
    The predicates in $G$ test features ($p$-values, effect sizes,
    fold changes) that are \emph{computed from the data during
    execution}, not specified in advance.
    A Snakemake rule ``if file exists'' tests a pre-known condition;
    \seqpipe\ tests ``is $p_\beta < 0.05$'' where $p_\beta$ was
    computed seconds earlier from a distance matrix.

  \item \textbf{Accumulation of findings.}
    The feature vector $\mathbf{x}$ is updated after each step
    (Equation~\ref{eq:interpret}).
    Step~$t$'s decision depends on what was found in
    steps~$1, \ldots, t{-}1$.
    For example, if both alpha and beta are non-significant, the
    engine skips more aggressively than if only one is
    non-significant.

  \item \textbf{Closed-loop re-evaluation.}
    The feedback arrow in Figure~\ref{fig:decision-graph} is not
    metaphorical: every 4 steps (or on a novelty spike), the engine
    re-inspects all data and re-evaluates the remaining plan.
    An unexpected finding in step~8 can alter the plan for step~12.
\end{enumerate}

We acknowledge that the decision \emph{rules} in $G$ are static---
they do not evolve within a run.
A fully autonomous system would update $G$ itself based on
accumulated experience (e.g., ``rarefaction confirmed the artifact,
so I should lower my confidence in all alpha results'').
This is a direction for future work.

The architecture (Figure~\ref{fig:architecture}) enforces a strict
separation of concerns.
Layers~1--2 are deterministic and LLM-free: they decide
\textit{what} to analyze.
Layer~3 uses the LLM to decide \textit{how} to analyze it
(code generation) and \textit{why} to investigate further
(hypothesis generation).
The system can reason about the optimal workflow without the LLM,
but cannot produce analysis outputs without it.

\subsection{Layer 1: DataInspector}

The DataInspector directly parses QIIME2-exported TSV files and
executes statistical tests in pure Python, without scipy, numpy,
or pandas dependencies.

For alpha diversity, sample values are partitioned by metadata group
and tested via Mann-Whitney $U$ (two groups) or Kruskal-Wallis $H$
(three or more groups).
The $U$ statistic uses rank transformation with tie correction:
\begin{equation}
  z = \frac{U - n_1 n_2 / 2}
           {\sqrt{\tfrac{n_1 n_2}{12}
                  \bigl( N + 1 - \tfrac{\sum_j (t_j^3 - t_j)}
                  {N(N-1)} \bigr)}}
\end{equation}
$p$-values use the Abramowitz--Stegun polynomial CDF approximation;
the $\chi^2$ survival function for $H$ uses the Wilson-Hilferty
transform~\citep{wilson1931}.
Effect sizes are computed as Cliff's $\delta$ (two groups) or
$\eta^2$ (multi-group).

For beta diversity, the full distance matrix ($O(n^2)$ entries) is
read, within- and between-group distances are separated, and a
pseudo-PERMANOVA~\citep{anderson2001} $F$-statistic is computed
with $p$-value from 199 permutations (fixed seed).
The between/within distance ratio provides an additional separation
metric.

For taxonomic differential analysis, the feature table and taxonomy
file are joined to compute genus-level relative abundances per
group, yielding fold change and absolute difference for each genus.

\subsection{Layer 2: EvalMediator and DecisionEngine}

Each completed step is scored on eight axes
(Table~\ref{tab:axes}) using the DataSnapshot from Layer~1.
The composite score $c_t = \sum_a w_a \cdot s_{t,a}$ aggregates
the weighted axis values.
The score matrix $\mathbf{A} \in \mathbb{R}^{T \times 8}$ is
compressed to three principal components via power-iteration SVD
on the centered covariance matrix.

The DecisionEngine encodes literature-based heuristics as
deterministic rules:
\begin{itemize}
  \item \textbf{Alpha} (Willis, 2019):
    $p < 0.05 \land d > 0.5 \Rightarrow$ add effect-size plot
    and rarefaction;
    $p < 0.05 \land d \leq 0.5 \Rightarrow$ add rarefaction only;
    $p \geq 0.05 \Rightarrow$ skip alpha follow-ups.
  \item \textbf{Beta} (Anderson, 2001):
    $p < 0.05 \Rightarrow$ add betadisper (mandatory);
    ratio $> 2 \Rightarrow$ add NMDS and pairwise PERMANOVA;
    $p \geq 0.05 \Rightarrow$ skip all beta follow-ups.
  \item \textbf{Taxonomy} (Gloor et al., 2017):
    fc $> 50$ at abundance $< 1\% \Rightarrow$ compositional
    artifact warning;
    $\geq 5$ genera with fc $> 2 \Rightarrow$ add functional
    prediction and indicator species.
  \item \textbf{Quality} (McMurdie \& Holmes, 2014):
    CV $> 0.5 \Rightarrow$ add rarefaction;
    sparsity $> 90\% \Rightarrow$ add prevalence-filtered reanalysis.
\end{itemize}

\subsection{Layer 3: LLM Code Generation and Hypothesis}

The LLM (qwen2.5-coder, 7B parameters, running locally via Ollama)
performs three functions:

\begin{enumerate}
  \item \textbf{Initial plan generation} (Phase~2):
    given the DataRecon summary and domain knowledge, the LLM
    proposes an ordered list of 12--20 analysis steps as JSON.
    On failure, a deterministic fallback
    (\texttt{build\_domain\_driven\_plan()}) generates the plan
    from the DataProfile without LLM involvement.
  \item \textbf{Analysis code generation} (Phase~3, each step):
    the LLM writes a complete Python script (matplotlib, pandas,
    seaborn) for each analysis step.
    If the code fails, the error message is passed back to the LLM
    for correction, up to three attempts.
    \textit{This is the function for which no deterministic
    alternative currently exists}; if the LLM fails all three
    retries, the step is recorded as failed and skipped.
  \item \textbf{Creative investigation hypotheses} (replanning):
    during adaptive replanning, the LLM proposes novel follow-up
    investigations (e.g., ``Is the 324$\times$ Bacteroides
    enrichment driven by loss of competing taxa?'').
    These are merged with DecisionEngine outputs via
    $\mathrm{merge}(d_{\mathrm{py}}, d_{\mathrm{llm}})$, where
    Python-determined skips override LLM-proposed additions.
\end{enumerate}

Under total LLM failure, the decision-making loop (Layer~2)
continues to operate: skip/add/reorder decisions are applied to the
plan queue, and the system logs which steps \textit{would have}
been executed.
However, no analysis outputs (figures, statistical results) are
produced, as code generation requires the LLM.
This architectural property means that the \textit{correctness of
workflow decisions} can be validated independently of code
generation quality---a separation we exploit in the evaluation.

\subsection{Execution Loop}

Algorithm~\ref{alg:loop} formalizes the loop.

\begin{algorithm}[t]
\caption{Adaptive Execution Loop}
\label{alg:loop}
\begin{algorithmic}[1]
\REQUIRE Dataset $D$, metadata $M$, plan $P_0$
\STATE $t \gets 0$
\WHILE{$P_t \neq \emptyset$}
  \STATE Execute $s_t \gets P_t.\mathrm{pop}()$ via LLM code generation (up to 3 retries)
  \STATE $\mathrm{snap}_t \gets \mathrm{DataInspector.inspect}(s_t)$
  \COMMENT{Layer 1}
  \STATE $\mathrm{score}_t \gets \mathrm{EvalMediator.evaluate}(\mathrm{snap}_t)$
  \COMMENT{Layer 2}
  \IF{$t \bmod 4 = 0$ \OR $\mathrm{score}_t.\mathrm{novelty} > 0.7$}
    \STATE $d_{\mathrm{py}} \gets \mathrm{DecisionEngine.decide}(P_t)$
    \COMMENT{deterministic}
    \STATE $d_{\mathrm{llm}} \gets \mathrm{LLM.replan}(\mathrm{state}, P_t)$
    \COMMENT{optional}
    \STATE $P_{t+1} \gets \mathrm{merge}(d_{\mathrm{py}}, d_{\mathrm{llm}}, P_t)$
  \ENDIF
  \STATE $t \gets t + 1$
\ENDWHILE
\end{algorithmic}
\end{algorithm}

\section{Evaluation}
\label{sec:eval}
% ======================================================================

We structure the evaluation around three questions:
(1)~Does the DecisionEngine make correct decisions?
(2)~Are those decisions robust to hyperparameter perturbation?
(3)~What is the LLM's actual contribution and bottleneck?

\subsection{Experimental Design}
\label{sec:eval-setup}

\paragraph{Datasets.}
We used four publicly available 16S rRNA amplicon datasets from the
QIIME2 documentation server: Moving Pictures (34 samples),
Atacama Soil (54 samples), Gneiss IBD (87 samples), and FMT Trial
(121 samples).
By varying the grouping variable within each dataset, we constructed
12 analysis scenarios spanning a spectrum from strong multi-category
signals to absent signals to incomplete data (Table~\ref{tab:comparison}).

\paragraph{Expert ground truth.}
For each of 21 downstream analysis steps, we defined whether an
expert would execute or skip it based on the observed data
characteristics.
The protocol is \textit{data-dependent but rule-deterministic}:
given a vector of data features
$\mathbf{x} = (\alpha_{\mathrm{sig}}, d_\alpha, \beta_{\mathrm{sig}},
\mathrm{ratio}, \mathrm{fc}_{\max}, n_{\mathrm{diff}}, \ldots)$,
the expert decision for each step is uniquely determined by
published heuristics~\citep{anderson2001,willis2019,gloor2017,mcmurdie2014}.
This protocol was defined independently of the DecisionEngine
implementation---though both encode the same domain knowledge,
making agreement necessary but not sufficient for validation.

\paragraph{Evaluation levels.}
We conducted three levels of evaluation, each answering a different
question:
\begin{enumerate}
  \item \textbf{Real-data evaluation} (Section~\ref{sec:eval-real}):
    12 scenarios $\times$ 10 runs = 2,520 decisions.
    \textit{Does the engine make correct decisions on actual microbiome data?}
  \item \textbf{Synthetic generalization} (Section~\ref{sec:eval-synth}):
    10,000 random data vectors $\times$ 21 steps = 210,000 decisions.
    \textit{Does accuracy generalize beyond the four available datasets?}
  \item \textbf{Weight invariance} (Section~\ref{sec:eval-weight}):
    10,000 random weight configurations $\times$ 12 real scenarios = 2,520,000 full EvalMediator executions.
    \textit{Do the 8-axis weights affect decisions?}
\end{enumerate}

In total, 2,732,520 per-step decision evaluations were performed.

\subsection{Weight Invariance}
\label{sec:eval-weight}

The EvalMediator computes a weighted composite score
$c = \sum_a w_a \cdot s_a$ from eight axis scores.
The weights $\mathbf{w} \in \Delta^7$ (the 7-simplex) were
initially hand-selected.
A natural question is whether different weights would produce
different---and potentially better---decisions.

We tested this at three scales:
\begin{enumerate}
  \item \textbf{Sensitivity analysis} (8 configurations):
    setting each axis weight to zero in turn.
    Result: $\Delta\text{accuracy} = 0$ for all 8 axes.
  \item \textbf{Grid search} (213 configurations):
    systematically varying the top-3 axis weights.
    Result: all configurations produced identical decisions.
  \item \textbf{Exhaustive random search} (10,000 configurations):
    sampling $\mathbf{w}$ from a Dirichlet distribution and running
    full EvalMediator initialization (TSV parsing + statistical tests
    + decision tree) on all 12 real-data scenarios.
    This required 120,000 full evaluations over 6.4~hours.
    Result: $\sigma = 0.0000000000$ across all 10,000 $\times$ 12
    = 120,000 runs.
\end{enumerate}

In total, \textbf{10,221 weight configurations produced
identical decisions across all scenarios}.
This is not coincidence but an architectural property:
inspection of the DecisionEngine source code confirms that the
\texttt{decide()} method accesses only raw $p$-values
(from \texttt{DataSnapshot.alpha\_group\_tests} and
\texttt{beta\_pvalues}), effect sizes (\texttt{effect\_size}),
fold changes (\texttt{group\_differential\_genera}), and data
availability flags---never the composite score or the weight vector.

\textbf{Theorem} (Weight Invariance): \textit{For any two weight
vectors $\mathbf{w}_1, \mathbf{w}_2 \in \Delta^7$ and any fixed
dataset $D$, the DecisionEngine produces identical skip/add
decisions: $\mathrm{decide}(\mathbf{w}_1, D) = \mathrm{decide}(\mathbf{w}_2, D)$.}

This renders weight optimization unnecessary and provides a
robustness guarantee: users cannot accidentally misconfigure the
system's decision logic by changing weights.
Weights affect only the composite score used for display and
novelty-spike replanning triggers (determining \textit{when} the
engine re-evaluates, not \textit{what} it decides).

\subsection{Validation}
\label{sec:eval-validation}

\paragraph{Statistical test accuracy.}
Pure-Python implementations were validated against scipy on 100
Monte Carlo datasets ($n = 8$--$30$).
Test statistics ($U$, $H$) were numerically identical;
$p$-values differed by MAE = 0.027 (Mann-Whitney) and 0.014
(Kruskal-Wallis) due to normal approximation vs exact methods.
Significance classification ($p < 0.05$) agreed in 99\% and 100\%
of trials.

\paragraph{Biological conclusions.}
Seven established conclusions of the Moving Pictures
dataset~\citep{qiime2} were tested against DataInspector outputs.
All seven confirmed: body-site distinction
($p = 6.7 \times 10^{-4}$, PERMANOVA $F = 112$),
\textit{Bacteroides} gut dominance (56.4\%), subject $\ll$ body-site
effect ($F = 33$ vs $F = 112$).

\paragraph{Reproducibility.}
120 runs (12 scenarios $\times$ 10 runs) produced identical
decisions and 8-axis scores.
This is guaranteed by construction: Layer~1 uses a fixed PERMANOVA
seed, and Layer~2 consists of deterministic conditionals.

\section{Limitations}
\label{sec:limits}
% ======================================================================

Several limitations constrain the current system.

The 7B LLM achieves only 54\% success on predefined analysis tasks
and 6\% on novel investigations.
Complex analyses (compositional regression, network inference)
frequently fail even after three retries.
The pure-Python statistical implementations use normal and $\chi^2$
approximations that are less accurate than exact tests for small
samples ($n < 20$); scipy-backed tests should be preferred in
production.
Decision tree thresholds ($p < 0.05$, $d > 0.5$, fc $> 5$) are
drawn from literature conventions, not optimized for specific
datasets; different research contexts may warrant different
thresholds.
The eight-axis weights are hand-selected; however, weight
invariance analysis (Section~\ref{sec:eval-weight}) demonstrated
that decisions are independent of the weight vector, rendering
this a cosmetic rather than functional limitation.
The system currently supports only 16S rRNA amplicon data.
The evaluation covers four datasets and seven scenarios; a
comprehensive validation would require additional experimental
designs (longitudinal, case-control with confounders) and
comparison with independent human experts rather than a
literature-derived protocol.

% ======================================================================
\section{Discussion}
\label{sec:discussion}
% ======================================================================

The central finding of this work is that the majority of analytical
decisions in a microbiome workflow can be made deterministically
from data, without LLM involvement.
Of the three functional categories identified in
Section~\ref{sec:eval-role}, only creative hypothesis generation
requires a language model, and even that function is currently
unreliable at 7B scale.
This suggests that the path to autonomous scientific analysis is
not primarily through larger language models, but through better
formalization of domain-specific reasoning as auditable,
deterministic rules.

The zero false-negative rate across 147 decisions is a stronger
safety guarantee than the accuracy percentage alone conveys.
A system that occasionally runs an unnecessary analysis
(false positive) wastes computation; a system that skips a
necessary analysis (false negative) misses a finding.
The DecisionEngine's conservative bias---it keeps steps when
uncertain---aligns with the scientific principle of not prematurely
discarding potentially informative analyses.

The accuracy floor of 52\% on taxonomy-absent datasets highlights
that adaptive decision-making is bounded by data completeness.
This is not a limitation of the decision logic but of the input:
without genus-level abundances, differential-abundance-dependent
decisions cannot be made.
This motivates future work on \textit{data-acquisition decisions}---
the system could recommend running additional upstream analyses
(e.g., taxonomy classification) when it detects that missing data
features limit its decision accuracy.

The LLM performance data (54\% registry, 6\% investigation)
provides a quantitative baseline for future model comparisons.
As local models scale from 7B to 30B+ parameters, we expect
Category~2 (code generation) success to increase substantially,
while Category~3 (hypothesis generation) may require fundamentally
different approaches such as retrieval-augmented generation or
tool-use frameworks.

% ======================================================================
\section{Conclusion}
\label{sec:conclusion}
% ======================================================================

We presented \seqpipe, a closed-loop system for adaptive microbiome
analysis that architecturally separates \textit{what to analyze}
(deterministic, LLM-free) from \textit{how to execute the analysis}
(LLM-assisted code generation).
Evaluation on seven scenarios from four public datasets
demonstrated that the deterministic DecisionEngine achieves up to
95\% expert agreement with zero false-negative skips and absolute
reproducibility.
The LLM remains essential for code generation (54\% success on
predefined tasks) and is the system's primary bottleneck: creative
investigations succeed at only 6\%, and the dominant error modes
(\texttt{NameError}, \texttt{KeyError}) reflect the 7B model's
limited capacity for code synthesis rather than reasoning.

The core design principle is that \textbf{workflow decisions should
be grounded in data, not in language model outputs}, while
acknowledging that \textbf{analysis execution currently requires
the LLM}.
This separation yields a system where decision correctness can be
validated independently of code generation quality---an architectural
property that enables targeted improvement of either component
without affecting the other.
As local LLMs scale to 30B+ parameters and template-based code
generation matures, we expect the execution bottleneck to narrow,
bringing the system closer to fully autonomous operation.
